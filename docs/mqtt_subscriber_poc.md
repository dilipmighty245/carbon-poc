# MQTT subscriber PoC

This standalone command checks broker connectivity, authentication, subscription
acceptance and receipt of real messages. It subscribes only; it does not publish
commands, connect directly to meters, or change the application's facility ingestion.

## Run against Instrutel

To watch events in a local terminal, run:

```sh
./scripts/run_mqtt_subscriber.sh
```

The script builds the subscriber, defaults to the supplied Instrutel broker,
topic and username, and prompts for the password without echoing it. An existing
`MQTT_PASSWORD` environment variable skips the prompt. Connection settings can
also be overridden through their environment variables. It streams events for
one hour without a message-count limit; press Ctrl+C to stop. When `jq` is
installed, it displays readable payloads and receipt metadata; otherwise it
prints the original JSONL. Connection and reception logs remain visible on
stderr. Extra subscriber flags override the defaults, for example:

```sh
./scripts/run_mqtt_subscriber.sh -duration 10m -max-messages 5
```

### Build and capture manually

From the repository root, build the command:

```sh
go build -o bin/mqtt-subscriber ./cmd/mqtt-subscriber
```

Set connection details in your shell. Obtain the password separately and supply it
through `MQTT_PASSWORD`; do not commit credentials or capture files.

```sh
export MQTT_BROKER_URL='tcp://15.207.187.242:1883'
export MQTT_TOPIC='INSTRUTEL/MBIOT_ETH/09001/EMS'
export MQTT_USERNAME='test'
export MQTT_PASSWORD='<provided separately>'

mkdir -p .dev-data/mqtt
./bin/mqtt-subscriber \
  -duration 60s \
  -max-messages 3 \
  -output .dev-data/mqtt/instrutel.jsonl
```

The supplied endpoint uses plain MQTT over TCP. Use `ssl://host:port` for a TLS
broker; server certificate verification remains enabled. Optional `MQTT_CA_FILE`,
`MQTT_CERT_FILE` and `MQTT_KEY_FILE` support custom CAs and mutual TLS. The client
uses MQTT 3.1.1. Confirm protocol version and supported QoS with Instrutel.

`-broker`, `-topic`, `-client-id`, `-qos`, `-connect-timeout`, `-duration` and
`-max-messages` are configurable. Run `-help` for all options. Credentials are read
only from environment variables. A unique client ID is generated by default.

The default subscription QoS is 0, pending provider confirmation. The command
reports the QoS actually granted by the broker. It stops after three messages or
60 seconds of observation following a successful subscription. Use
`-max-messages 0` to observe for the entire duration. An initial failed connection
ends with an error; a lost established connection triggers reconnect and
resubscription within the original observation window.

## Output and interpretation

Status messages go to stderr. Each received message produces one JSONL record
containing the UTC receipt time, topic, delivered QoS, retained/duplicate flags,
payload length, and `payload_base64` containing the exact original bytes.
UTF-8 payloads also include `payload_text` for inspection. No meter format or
vendor field names are assumed. Receipt time is not the meter observation time.

Omit `-output` to emit JSONL to stdout. A capture file is appended to, with mode
0600 for a new file. `.dev-data/` is already ignored by Git.

Exit codes:

- `0`: At least one message captured, or the operator stopped the command.
- `1`: Configuration, connection/authentication, subscription or capture failure.
- `2`: Subscription succeeded but no message arrived in the observation window.

A successful subscription alone does not prove the meter is publishing. Check
the retained flag and the payload's own observation timestamp before calling a
received message a fresh measurement. This PoC uses clean sessions and has no
durable restart checkpoint, payload validation, deduplication, consumption
calculation or dashboard integration. Those follow after inspecting real data.

## Local verification

```sh
go test -race ./cmd/mqtt-subscriber
```

Tests use a local MQTT protocol fixture, never the provider endpoint. They cover
connection credentials and MQTT 3.1.1 settings, authentication rejection,
subscription rejection/missing or invalid grants, subscription timeout,
no-message outcomes, exact JSON/binary/empty payload capture, message limits,
capture-write failure, cancellation and reconnect/resubscription. Configuration
tests also cover topic filters and TLS verification defaults. The test runner
needs permission to bind loopback sockets. The live check requires network access
to Instrutel and a publishing device.

All three payloads are JSON objects. They share `SNO=09001` and report distinct


There is no measurement timestamp or event/sequence ID in these samples.
Broker delivery is verified; measurement freshness and whether the provider is
forwarding physical meter readings still require provider confirmation. The
three messages arrived together, so this check does not establish the publishing
interval. Confirm field definitions, units/scaling, the meaning of `COMM`, and
whether `kWh` is cumulative or interval energy before building calculations.
